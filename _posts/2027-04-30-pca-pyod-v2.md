## Introduction

Every day, we build on code we have never read. When we choose a library, we skim its documentation, check that others use it, and move on. Few researchers read the source code in detail. Generative AI widens this gap, as more code and text are produced without anyone working through every detail. Shah <d-cite key="researchAskingAuthorsTheir2026"></d-cite> reports that papers are being submitted that the authors cannot explain and that appear to be AI-generated. If authors do not fully understand their papers, it is even less likely that the underlying libraries are checked for errors.

Reproducibility does not protect against this. Pinned versions make results reproducible: the same code yields the same results <d-cite key="nasem2019reproducibility"></d-cite>. Whether the code implements the method it is attributed to is a separate question, known as code verification <d-cite key="roy2005verification"></d-cite>. Published papers are fixed, but the underlying code can change. At the moment, there isn't a mechanism to inform authors, reviewers and readers that the code is not implemented as described in the references.

We came across such a case while studying Principal Component Analysis (PCA)-based anomaly detection with [PyOD](https://github.com/yzhao062/pyod) <d-cite key="zhao2019pyod"></d-cite>. It documents its PCA detector with a reference to the principal component classifier (PCC) of Shyu et al. <d-cite key="shyu2003"></d-cite> and the PCA-based methods described by Aggarwal <d-cite key="aggarwal2017"></d-cite>. However, the calculation of the anomaly score implemented in PyOD deviates from the one described in these references. With PyOD describing itself as the most widely used Python library for anomaly detection <d-cite key="yzhao062"></d-cite>, the deviating score has propagated into research, such as the ADBench benchmark <d-cite key="NEURIPS2022_cf93972b"></d-cite> and into products such as PostHog <d-cite key="posthog"></d-cite>.

First, we take the case apart. We recap what the cited method computes, show where PyOD deviates from it, and propose a fix. Second, we ask how far the deviating score has spread, why it survived although it has been reported publicly since 2019, and what is missing to make such problems visible. We close with a proposal for correctness advisories that build on existing infrastructure.

## Case study: PCA in PyOD

### What the cited method computes

Principal Component Analysis (PCA) is a classical method for dimensionality reduction <d-cite key="Jolliffe2002Principal"></d-cite>. It identifies orthogonal directions, the principal components, ordered by how much of the data's variance they explain. The idea behind PCA-based outlier detection is that data points lying outside the subspace spanned by the principal components are classified as outliers. While dimensionality reduction typically retains only the major principal components to capture dominant variance, PCA-based anomaly detection can additionally exploit the minor components. The major components describe the dominant variation of normal data. The minor components have minimal variance and indicate near-linear dependencies among the features, so they are sensitive to observations that break the correlation structure <d-cite key="shyu2003"></d-cite>.

Shyu et al. <d-cite key="shyu2003"></d-cite> describe a principal component classifier for anomaly detection. We summarize the parts needed for the anomaly score. The full classifier is described in [Appendix A](#appendix-a). Each feature is first standardized with its sample mean and variance, which moves the centroid of the data to the origin and gives every feature unit variance. We denote a standardized observation by $$\mathbf{z} = (z_1, \dots, z_p)^\top$$.

**Principal components**\
Eigenvalues and eigenvectors are calculated via eigenvalue decomposition from the $$p \times p$$ correlation matrix $$\mathbf{R}$$. This is the covariance matrix of the standardized values $$\mathbf{z}$$. It yields $$p$$ pairs of the eigenvalue and unit eigenvector $$(\lambda_i, \mathbf{e}_i)$$, ordered such that $$\lambda_1 \geq \lambda_2 \geq \dots \geq \lambda_p$$.

The key quantity is the $$i$$-th principal component score $$y_i$$. It is calculated by projecting each standardized observation $$\mathbf{z}$$ onto the $$i$$-th eigenvector $$\mathbf{e}_i$$:

<p>
$$y_i = \mathbf{e}_i^\top \mathbf{z} = e_{i1} z_1 + e_{i2} z_2 + \dots + e_{ip} z_p $$
</p>

The score $$y_i$$ has variance $$\lambda_i$$ on the training data, so $$y_i^2 / \lambda_i$$ represents the squared, variance-normalized distance from the origin along the $$i$$-th principal axis. The sum of $$y_i^2/\lambda_i$$ over all $$p$$ components yields the squared Mahalanobis distance <d-cite key="shyu2003"></d-cite>, which is referred to by Aggarwal <d-cite key="aggarwal2017"></d-cite> as *soft PCA*.

**Major and minor components**\
Instead of summing over all components, Shyu et al. evaluate the first $$q$$ (major) and the last $$r$$ (minor) components with two separate statistics, $$T_{\text{major}}$$ and $$T_{\text{minor}}$$, each a sum of $$y_i^2/\lambda_i$$ over its components ([Appendix A](#appendix-a)). In the minor statistic, the weight $$1/\lambda_i$$ amplifies small deviations that violate the normal correlation structure. An observation is flagged as anomalous if either statistic exceeds its threshold.

### What PyOD computes

PyOD's PCA detector standardizes the data, fits scikit-learn's [PCA](https://scikit-learn.org/stable/modules/generated/sklearn.decomposition.PCA.html) <d-cite key="scikitlearn"></d-cite>, and scores observations with the explained variance ratios as weights. This pipeline deviates from the principal component classifier of Shyu et al. in several steps, which we list in [Appendix B](#pyods_pca). Most of these deviations are simplifications. The score, however, is a different function. We analyze PyOD's PCA in version `3.6.8` <d-cite key="pyodPCA368"></d-cite>.

With the default parameters, PyOD computes the score as follows <d-cite key="pyodPCA368"></d-cite>:

```python
# fit: learned from the standardized training data
self.selected_components_ = self.detector_.components_
self.selected_w_components_ = self.detector_.explained_variance_ratio_
# decision_function: X = standardized observations
np.sum(cdist(X, self.selected_components_) / self.selected_w_components_, axis=1)
```

The rows of `components_` are the unit eigenvectors $$s_i\mathbf{e}_i$$, with a sign $$s_i \in \{-1,+1\}$$ that scikit-learn sets by convention ([Problem 2](#problem-2)). The call to `cdist` measures the Euclidean distance from each observation to each eigenvector, treated as a *point* at the tip of the unit vector. This is neither the distance to the principal axis nor the projection $$y_i$$. Each distance is then divided by the explained variance ratio $$\lambda_i / \sum_j \lambda_j = \lambda_i / p$$, and the results are summed over all components:

<p>
$$
\text{score}_{\text{PyOD}}(\mathbf{z}) = p \sum_{i=1}^{p} \frac{\lVert \mathbf{z} - s_i\, \mathbf{e}_i \rVert}{\lambda_i},
\qquad s_i \in \{-1, +1\}.
$$
</p>

It deviates from the cited references in two fundamental ways.

<a id="problem-1"></a>
### Problem 1: The score is close to the norm

Each term of the score is the distance from $$\mathbf{z}$$ to an eigenvector tip $$s_i \mathbf{e}_i$$, multiplied by the weight $$p/\lambda_i$$. All tips lie at distance 1 from the center, because they are unit vectors. The distance from $$\mathbf{z}$$ to a tip is therefore almost the same as the distance from $$\mathbf{z}$$ to the center: by the triangle inequality, it is at least $$\lVert \mathbf{z}\rVert - 1$$ and at most $$\lVert \mathbf{z}\rVert + 1$$. Every term is thus roughly $$\lVert \mathbf{z}\rVert$$ times its weight, and the whole score is roughly

<p>
$$
\text{score}_{\text{PyOD}}(\mathbf{z}) \approx W \cdot \lVert \mathbf{z}\rVert, \qquad W = p\sum_{i=1}^{p} \frac{1}{\lambda_i}.
$$
</p>

$$W$$ depends only on the eigenvalues of the training data and is the same for every sample. The score is therefore essentially the distance to the center, multiplied by a constant. The direction in which a sample deviates can shift its score by at most $$\pm W$$, i.e. by as much as one unit of norm would.

**When the eigenvalues enter**\
The key difference lies in when the eigenvalues enter the score. Shyu et al. first scale each direction separately and then measure the distance, so each component score $$y_i$$ is divided by $$\sqrt{\lambda_i}$$. That means a small step along a minor component counts as much as a large step along a major one. PyOD does it the other way round. It first computes the Euclidean distance to the tip $$s_i \mathbf{e}_i$$, in which all directions count equally, and only afterwards divides by $$\lambda_i$$. This division scales the whole distance by the same factor, no matter in which direction the sample deviates. The information about which directions are normal is therefore lost before the eigenvalue is even applied.

The norm ignores how the features are correlated, which is exactly the structure PCA is meant to capture. Correlation-breaking anomalies that are not unusually far from the center are therefore hard to detect. The effect grows with the dimension: for standardized data, $$\mathbb{E}\lVert \mathbf{z}\rVert^2 = \operatorname{tr}(\mathbf{R}) = p$$, so on average $$\lVert \mathbf{z}\rVert \approx \sqrt{p}$$ and the tolerance of $$\pm 1$$ shrinks relative to the norm. This matches issue #64 <d-cite key="pyodIssue64"></d-cite>, where the PCA scores correlated at 0.99 with the distance to the origin.

The following figure illustrates this ($$\rho = 0.99$$, standardized). Shyu's contours of equal score are ellipses, stretched along the major and squeezed along the minor components. PyOD's terms have circular contours around the eigenvector tips, and away from the center their sum looks like circles around the center. The anomalies in the figure break the correlation but lie close to the center. Their norm is at most 1.6, while 10 % of the inliers lie farther out along the major axis. PyOD's threshold is therefore set by these inliers, all anomalies fall inside it and none is detected. Our proposed fix (aka Shyu's score) weights each direction by its eigenvalue before measuring the distance, which yields ellipses along the data and detects 26 of 30 anomalies.

<a id="problem-2"></a>
### Problem 2: The sign

scikit-learn computes the components via a singular value decomposition of the standardized data. The resulting components are only determined up to their sign. If $$\mathbf{e}_i$$ is a unit eigenvector of $$\mathbf{R}$$, so is $$-\mathbf{e}_i$$. scikit-learn fixes the sign by a convention (`svd_flip`) <d-cite key="sklearnPCA"></d-cite>, and the resulting sign has no meaningful interpretation in terms of the data <d-cite key="broResolvingSignAmbiguity2008"></d-cite>. Expanding the numerator of PyOD's score ([Appendix C](#appendix-c)) shows why this matters:

<p>
$$
\lVert \mathbf{z} - s_i \mathbf{e}_i \rVert = \sqrt{\lVert \mathbf{z}\rVert^2 - 2\, s_i\, y_i + 1}.
$$
</p>

Shyu's score contains $$y_i^2$$, so the sign of $$\mathbf{e}_i$$ cancels out. In PyOD's $$s_i y_i$$ the sign matters. Flipping it changes the scores and can therefore change the ranking of observations, as already reported in issue #217 <d-cite key="pyodIssue217"></d-cite>.

**Consequences for anomalies**\
Each term of PyOD's score measures how far a sample is from the tip of an eigenvector $$s_i \mathbf{e}_i$$, and this tip lies on only one side of the center. Consider two observations that deviate from the center by the same amount along $$\mathbf{e}_i$$, but in opposite directions. The sample on the side of the tip moves closer to it, so its term shrinks. The sample on the other side moves away from it, so its term grows. For Shyu et al., both observations are equally anomalous. For PyOD, one of them looks less anomalous, and which one is decided by the sign convention, not by the data.

The effect is strongest for the minor components, because their terms carry the largest weights $$p/\lambda_i$$. In the extreme case, a sample lies exactly at the tip, $$\mathbf{z} = s_i \mathbf{e}_i$$. For Shyu et al., this is probably an anomaly with score $$1/\lambda_i$$. For PyOD, its distance to the tip is zero, so exactly the term with the largest weight vanishes.

The following figure illustrates this on two correlated features ($$\rho = 0.9$$) with 15 anomalies that break the correlation. With PyOD's score (left), the contours are circles whose center is shifted from the centroid towards the tip $$s_2\mathbf{e}_2$$ of the minor eigenvector, here to the lower right. Anomalies on this side lie close to the tip, so their scores stay below the decision threshold. Anomalies on the opposite side are farther from the tip and are more likely to be detected. Which side is favored depends only on the sign convention. With the corrected score that we derive [below](#fix) (right), the contours are ellipses centered at the centroid, so anomalies on both sides are treated equally.

### A short example

Consider $$p = 2$$ standardized sensors with correlation $$\rho = 0.95$$, so that $$\lambda_1 = 1.95$$, $$\mathbf{e}_1 = \tfrac{1}{\sqrt 2}(1, 1)$$ and $$\lambda_2 = 0.05$$, $$\mathbf{e}_2 = \tfrac{1}{\sqrt 2}(1, -1)$$. In Shyu's classifier, $$q = r = 1$$. We score a few observations with Shyu's statistics and with PyOD under both signs of $$\mathbf{e}_2$$:

| Observation | description | PyOD, $$s_2 = +1$$ | PyOD, $$s_2 = -1$$ | soft (Shyu) |
|---|---|---|---|---|
| $$0$$ | training mean | 41.03 | 41.03 | 0.00 |
| $$A = (2, 2)$$ | follows the correlation | 121.88 | 121.88 | 4.10 |
| $$B = (1.5, -1.5)$$ | breaks the correlation | 47.26 | 127.26 | 90.00 |
| $$\mathbf{e}_2$$ | tip of the minor eigenvector | 1.45 | 81.45 | 20.00 |
| $$-\mathbf{e}_2$$ | its mirror image | 81.45 | 1.45 | 20.00 |

For Shyu et al., $$B$$ is by far the most anomalous sample, and $$A$$ is unremarkable. PyOD with $$s_2 = +1$$ ranks $$A$$ well above $$B$$, because $$A$$ lies farther from the center ([Problem 1](#problem-1)). Flipping the sign of $$\mathbf{e}_2$$ reverses the order of $$A$$ and $$B$$ and swaps the scores of the two tips ([Problem 2](#problem-2)). Whichever tip coincides with $$s_2 \mathbf{e}_2$$ scores lower than the training mean itself.

### The fix
Our fix adopts the projection proposed in PR #211 <d-cite key="pyodPR211"></d-cite>, but normalizes by the eigenvalues $$\lambda_i$$ instead of the explained variance ratios. Relative to PyOD 3.6.8, the change is:
```diff
- self.w_components_ = self.detector_.explained_variance_ratio_
+ self.w_components_ = self.detector_.explained_variance_
  ...
- return np.sum(cdist(X, self.selected_components_)
-               / self.selected_w_components_, axis=1).ravel()
+ projections = (X - self.detector_.mean_) @ self.selected_components_.T
+ return np.sum(projections ** 2 / self.selected_w_components_,
+               axis=1).ravel()
```
This resolves both problems. Normalizing each principal direction by its eigenvalue $$\lambda_i$$ ensures that the correlation structure is preserved ([Problem 1](#problem-1)). Because $$y_i$$ enters the statistic squared, the anomaly score is invariant to the sign of the eigenvectors ([Problem 2](#problem-2)). With the default parameters, the score equals the squared Mahalanobis distance, i.e., Aggarwal's soft PCA. If `n_components` $$= p$$ and `n_selected_components` $$= r$$, it corresponds to the minor statistic $$T_{\text{minor}}$$ of Shyu et al.

## How far it spread

PyOD has been downloaded more than 46 million times <d-cite key="yzhao062"></d-cite>. To estimate how far the deviating score has spread, we searched for code that uses the detector and papers that report its results.

Using the GitHub code search API <d-cite key="githubCodeSearchAPI"></d-cite>, we searched for all import styles of PyOD’s PCA, such as `from pyod.models.pca import PCA` or `import pyod.models.pca`. On 10 November 2026, this returned 910 unique files in 525 repositories, excluding forks of PyOD. They range from small projects to widely used products like PostHog (40k stars) or TDengine (25k stars).

With current library versions, PyOD's PCA fails on six of the datasets because zero eigenvalues lead to infinite scores, so we compare both detectors on the remaining 51. On average, ROC AUC rises from 0.718 to 0.744, while the average precision drops from 0.357 to 0.320. Neither difference is significant (two-sided Wilcoxon signed-rank test <d-cite key="wilcoxon1945individual"></d-cite>). The changes per dataset, however, are large in both directions. For example, ROC AUC rises for vowels from 0.656 to 0.912, while AP drops for satimage-2 from 0.858 to 0.436.

ADBench pins `pyod==1.0.0` <d-cite key="adbenchRequirements"></d-cite>, whose scoring code is identical to `3.6.8` <d-cite key="pyodPCA100"></d-cite>. Its PCA results are therefore reproducible, but the code behind them is not verified. They were not computed with the method of Shyu et al. that PyOD cites. The numbers are a correct measurement of PyOD's implementation, but they are reported under a method whose cited definition they do not follow.

ADBench has been cited 865 times <d-cite key="NEURIPS2022_cf93972b"></d-cite> and the PyOD paper 1484 times <d-cite key="zhao2019pyod"></d-cite>, although not every citing work uses the PCA detector. To estimate how many publications depend on the deviating implementation, we complemented the repository search with a literature search. We queried OpenAlex and Semantic Scholar for papers that use PCA and link to a public GitHub repository relying on PyOD’s implementation. The search identified 67 papers, among them "Conformal prediction interval for dynamic time-series" (416 citations) <d-cite key="xuConformalPredictionInterval2021"></d-cite>, PIDForest (49 citations) <d-cite key="PIDForestAnomalyDetection2019"></d-cite>, and UADB (24 citations) <d-cite key="yeUADBUnsupervisedAnomaly2023"></d-cite>. All citation counts were retrieved from Google Scholar on 15 November 2026.

Two limitations apply to this number. First, 23 of the 67 papers are indexed with arXiv as their venue and only some of them were later published elsewhere. Second, the search identifies only papers whose own code imports or copies the implementation. A paper that copies PCA results from a benchmark such as ADBench reports affected numbers without importing PyOD. The 67 papers are therefore a lower bound on the number of publications that report affected results.

There is currently no systematic way to answer the question: which published results depend on this code?

## Why it survived

This is not meant to blame the PyOD maintainers. A library of this reach is a huge service to the community, and we use it ourselves. Mistakes happen in every codebase, ours included. What interests us is how this one survived for so long. Three observations stand out.

**The documentation cites the method, the code does not implement it.**
The code comment introduced in commit [a6f05f3b](https://github.com/yzhao062/pyod/commit/a6f05f3be9cddeea2e5a57f6c9c7cbb05efd9723) described exactly the computation of the current score. It was later replaced by the references to Shyu et al. <d-cite key="shyu2003"></d-cite> and Aggarwal <d-cite key="aggarwal2017"></d-cite>, while the code remained unchanged. Anyone reading the documentation therefore has good reason to assume that the detector implements the cited method. Such drift between comments and code is common <d-cite key="wen2019codecomment"></d-cite>.

**The problem was reported, but not fixed.**
In 2019, a user observed on his data that the PCA scores correlate with the Euclidean distance to the origin ($$r = 0.99$$), which is [Problem 1](#problem-1). The maintainer closed the issue, attributing this to the data <d-cite key="pyodIssue64"></d-cite>. In 2020, pull request #211 <d-cite key="pyodPR211"></d-cite> implemented the correct projection, and issue #217 <d-cite key="pyodIssue217"></d-cite> pointed out that the ranking depends on the sign of the components, which is [Problem 2](#problem-2). In 2021, pull request #340 <d-cite key="pyodPR340"></d-cite> took up the idea of #217. None of these proposals has been merged to date, and each of them deviates from the cited method in its own way ([Appendix D](#appendix-d)).

**Adoption continued.**
Although the deviation had been public since 2019, ADBench adopted the detector as a baseline in 2022. From there, its results spread into papers that copy benchmark numbers without ever importing PyOD.

Reporting a problem is therefore not enough. The report lives in an issue tracker, while the affected results live in papers, and nothing connects the two.

## What is missing

This case is not unique to PyOD. Kriegel et al. showed that runtime evaluations often compare implementations rather than algorithms <d-cite key="kriegel2017black"></d-cite>, and Engstrom et al. found that undocumented implementation details account for much of the reported advantage of a popular deep reinforcement learning algorithm <d-cite key="engstromImplementationMattersDeep2020"></d-cite>. Guides to machine learning pitfalls help authors avoid such errors before publication <d-cite key="lones2024pitfalls"></d-cite>. A deviation from the cited method, however, is hard to catch, since it raises no error <d-cite key="tambon2024silent"></d-cite> and the correct output is often unknown <d-cite key="kanewala2014testing"></d-cite>. None of these approaches covers what happens to published results once a deviation becomes known.

A fix in the library does not reach published results, but their pinned versions make it possible to determine whether they are affected. This requires a record of which code and versions are affected, a record of which code and versions a result depends on, and a way to link the two. Existing practices provide only parts of this. Pinned versions record the dependencies, but there is nothing to match them against. Changelogs cover only problems that have been fixed, and they do not link them to specific functions and versions in a machine-readable form. Issue trackers describe open problems, but they are scattered across repositories and not linked to affected versions. Rerunning every result would make matching unnecessary, but it would shift the cost to every reader of every paper.

Even where infrastructure exists, correcting the record is hard. Retracted papers keep being cited <d-cite key="hsiao2021continued"></d-cite> despite standardized retraction notices <d-cite key="niso2024crec"></d-cite>, and withdrawn datasets keep circulating through derivatives <d-cite key="peng2021mitigating"></d-cite>. These mechanisms also work on whole papers or datasets, not on individual results affected by a library.

For security vulnerabilities, this infrastructure exists. CVE started because every tool kept its own, incompatible list of vulnerabilities <d-cite key="mann1999cve"></d-cite>. Today, the OSV schema records affected package versions in a machine-readable format and is exported by GitHub Security Advisories, the PyPI Advisory Database and others <d-cite key="osvschema"></d-cite>. Tools such as pip-audit <d-cite key="pipAudit"></d-cite> and Dependabot <d-cite key="dependabot"></d-cite> match a project's dependencies against these records automatically, although records alone do not ensure action <d-cite key="kula2018developers"></d-cite>. In security, a published vulnerability is no cause for embarrassment. Known deviations should be treated the same way: what matters is not that they occurred, but that they become visible and get fixed.

## A proposal for a community-wide solution
We propose correctness advisories that link a known deviation in a library to the published results it affects. Most of the required parts already exist. Coordinated flaw disclosure describes how flaws in deployed machine learning models are reported and resolved <d-cite key="cattell2024cfd"></d-cite>. The AI Vulnerability Database separates a general vulnerability from the individual reports of its occurrence <d-cite key="avid"></d-cite>. Both, however, address deployed models and their providers, not libraries or the published results that depend on them. To close this gap, we propose four building blocks.

**Provenance**
Repositories would pin exact versions, for example in a lockfile. Papers would state for each baseline whether it was computed (library and version) or copied (source) <d-cite key="smith2016software"></d-cite>. Copying results would remain legitimate, but become traceable.

**Advisories**
We suggest modeling advisories on the OSV schema <d-cite key="osvschema"></d-cite>. They would keep OSV's fields for identifiers, affected versions and references, replace its security severity with the impact on results, and add the type of deviation, the cited method and a status. An advisory could also name the affected functions, so that matching can check whether a project actually calls them, as the Go vulnerability database does <d-cite key="govulndb"></d-cite>. For PyOD, an advisory could look as follows:
```yaml
id: MLCA-2026-0001
modified: "2026-11-18T00:00:00Z"
summary: PCA score deviates from the cited methods
type: deviation-from-cited-method
cited_method: [Shyu et al. 2003, Aggarwal 2017]
impact: ranking          # values | ranking | classification
status: confirmed        # reported | confirmed | disputed | fixed
affected:
  - package: {ecosystem: PyPI, name: pyod}
    ranges: [{type: ECOSYSTEM, events: [{introduced: "0"}]}]   # no "fixed" event: still open
    symbols: [pyod.models.pca.PCA.decision_function]
references:
  - {type: REPORT, url: "https://github.com/yzhao062/pyod/issues/64"}   # further: #217, #211, #340
```

Since one advisory can affect many results, identified at different times and with varying certainty, we propose a separate record for each affected result. Its status could follow VEX <d-cite key="cisa2023vex"></d-cite>, where `not_affected` requires a justification:
```yaml
id: MLCR-2026-0001
advisory: MLCA-2026-0001
result: ADBench (NeurIPS 2022), PCA results in Fig. 4a/c, Fig. 5a–d, Fig. 7a/d, and Appx. D
status: affected       # under_investigation | affected | not_affected (+ justification) | fixed
evidence: pins pyod==1.0.0, scoring code identical to 3.6.8
```
For ADBench, the evidence is the identical scoring code <d-cite key="pyodPCA100"></d-cite>. A record would remain `under_investigation` until someone has checked the public code and paper. This check would be done once and could be reused. Advisories and records could be hosted in a public Git repository with one file per entry, curated via pull requests.

Maintainers could contribute by adding a dedicated changelog category for changes that alter results for the same data and parameters, as scikit-learn already maintains <d-cite key="sklearn13changelog"></d-cite>. Such entries would translate directly into advisories with a fixed event in the affected version range.

**Matching**
A tool modeled on dependency audits such as pip-audit <d-cite key="pipAudit"></d-cite> could check a repository’s dependencies, including transitive ones, against the affected version ranges. Because version information alone overestimates how many projects are affected <d-cite key="pashchenko2022vuln4real"></d-cite>, the tool should then keep only repositories that import or call an affected function <d-cite key="ponta2020detection"></d-cite>. Copied results could be matched through the provenance statement of the citing paper, similar to detectors that flag papers citing retracted work <d-cite key="cabanac2024chain"></d-cite>. A citation alone would yield at most `under_investigation`. We propose restricting matching to direct reuse, since chains of copied results quickly weaken the evidence. A new advisory would trigger the same search in reverse, as we performed manually in [How far it spread](#impact).

**Visibility**
Warnings are most effective where researchers already work, like a dependency audit when code is run, a citation manager check when a paper is cited and the same check during review. Zotero already warns before retracted works are cited <d-cite key="zotero2019retraction"></d-cite>, and since it supports third-party plugins <d-cite key="zoteroPluginDev"></d-cite>, a similar check could be offered without changes to Zotero itself. Unlike a retraction notice, such a warning would refer to a specific result, e.g. the PCA results in ADBench, not to the paper as a whole.

### Limitations
Our proposal is a first sketch and leaves several questions open.

**What counts as a deviation** Independent implementations of the same algorithm often produce slightly different results <d-cite key="herbold2023differential"></d-cite>, and PyOD's biased standard deviation has little effect. An advisory would therefore need a criterion, e.g. that the deviation changes the ranking on a toy example. Disagreements between reporters and maintainers are to be expected. Coordinated flaw disclosure handles them with a panel of independent adjudicators that decides when a vendor rejects a report <d-cite key="cattell2024cfd"></d-cite>, and a similar panel could decide whether a deviation is recorded.

**Precision of matching** Matching on imports misses models instantiated by name (as in PyCaret), copied source code and unpublished code, and existing papers contain no provenance statements. For the existing literature, matching will therefore mostly produce records that require manual review.

**Affected does not mean wrong** A confirmed record states that the reported numbers were not obtained with the cited method. It does not state that the conclusions of the paper are wrong. In the fMRI case, a long-standing bug in a widely used package was confirmed <d-cite key="eklund2016cluster"></d-cite>, but its maintainers judged its impact minor <d-cite key="cox2017fmri"></d-cite>. In ADBench, PCA is one of 30 baselines, and whether the overall findings change requires a separate analysis.

**Evaluation** Beyond the manual search in [How far it spread](#impact), we have not evaluated whether automated matching is precise enough or whether warnings change how researchers reuse results.

**Sustainability** Advisories have to be maintained over many years. Security advisory databases show that this is possible, but it requires an institution to host them, not just a small group of volunteers.

## Conclusion

PyOD’s PCA detector cites Shyu et al., but scores observations by a weighted sum of Euclidean distances to the eigenvector tips instead of by variance-normalized projections. This score depends on the arbitrary sign of each eigenvector and is approximately proportional to the distance from the center. The detector is therefore largely insensitive to anomalies that violate the correlation structure without lying far from the center, which are precisely the anomalies the minor components are meant to detect. Replacing the distances with squared projections normalized by the eigenvalues makes the score sign-invariant and turns it into the squared Mahalanobis distance.

The corrected detector is not uniformly better. On ADBench, ROC AUC and AP change substantially in both directions depending on the datasets. Our main finding is therefore not a performance gain. It is that the PCA results reported in ADBench, at least 67 papers and 525 repositories were obtained with a score other than the one described in the cited references, although the deviation has been reported since 2019.

These results are reproducible, but the code behind them is not verified. This does not mean that the conclusions of the affected papers are wrong, only that their PCA numbers do not come from the cited method. Fixing the detector does not reach these results, and nothing currently connects a known deviation to the results it affects. Beyond this case, we sketched how known deviations could be made as visible as known vulnerabilities, largely by combining existing pieces: coordinated flaw disclosure, advisories modeled on OSV, VEX-style records for affected results, provenance statements in papers, and warnings in tools researchers already use.

### Future Work
Our fix deliberately changes only the score, so that its effect on ADBench can be attributed to this single component. The remaining parts of the PCC, namely trimming, separate major and minor statistics, and two thresholds, are not implemented in PyOD. Such components can substantially change the behavior of a method. A natural next step is to implement the full PCC as a separate detector class and to evaluate its components one at a time. This requires an additional design decision, because the PCC is a classifier with two thresholds, whereas benchmarks such as ADBench evaluate a single continuous score.

For the proposal, governance, the exact status workflow and automated matching remain open design questions. Lessons from establishing CVE are a starting point <d-cite key="baker1999cve"></d-cite>.

### Final Thoughts

Popularity is not proof of correctness <d-cite key="soergel2015rampant"></d-cite>. A widely used library may even be checked less, because everyone assumes someone else already has.

Generative AI cuts both ways here. Code written by humans, mistakes included, becomes training data, so an implementation like this one can resurface in generated code <d-cite key="jesseLargeLanguageModels2023"></d-cite>. At the same time, comparing an implementation with its documentation or the paper it cites is exactly the kind of tedious task where LLMs can help, although current models still miss more than half of real paper–code discrepancies <d-cite key="baumgartner2026scicoqa"></d-cite>. As Shah <d-cite key="researchAskingAuthorsTheir2026"></d-cite> reminds us, authors remain responsible for everything they publish, whether written by hand or with AI. We think this responsibility extends to the tools a paper builds on.

Advisories help once a problem is known. Finding it in the first place still depends on individual researchers. We therefore recommend: before you report results for a method, check that its implementation does what the paper says. Read the scoring function, look at the open issues, and test it on a toy example where you know the answer. An LLM can do a first pass.

## Appendix A
**The full principal component classifier**

**Standardization**\
Since the features are measured on different scales, features with large numerical ranges would dominate the principal components. Each feature $$k$$ is therefore standardized using its sample mean and sample variance over all $$n$$ time steps $$j$$:

<p>
$$
\bar{x}_k = \frac{1}{n}\sum_{j=1}^{n} x_{jk}, \qquad
s_{kk} = \frac{1}{n-1}\sum_{j=1}^{n} \left(x_{jk} - \bar{x}_k\right)^2
$$
</p>

The factor $$\frac{1}{n-1}$$ yields an unbiased variance estimate, since the mean itself is estimated from the same data. The standardized observation $$\mathbf{z}_j$$ is then

<p>
$$
z_{jk} = \frac{x_{jk} - \bar{x}_k}{\sqrt{s_{kk}}}, \qquad
\mathbf{z}_j = (z_{j1}, z_{j2}, \dots, z_{jp})^\top
$$
</p>

**Trimming**\
To make the PCC more robust against outliers in the training data, the $$\gamma \cdot n$$ observations with the largest Mahalanobis distances <d-cite key="mahalanobis1936generalized"></d-cite> are removed, as they might represent extreme values (e.g. $$\gamma=0.005$$ in <d-cite key="shyu2003"></d-cite>). Afterwards, mean and correlation matrix are reestimated from the remaining observations.

**Major and minor components**\
Instead of summing over all components, Shyu et al. evaluate the major and minor components using two separate statistics.

- The major statistic sums over the first $$q$$ components, where $$q$$ is the smallest number of components that together explain more than $$50\%$$ of the total variance. It detects observations with extreme values along the dominant directions.

  <p>
  $$T_{\text{major}}(\mathbf{z}) = \sum_{i=1}^{q} \frac{y_i^2}{\lambda_i}.$$
  </p>

- The minor statistic sums over the last $$r$$ components with eigenvalues $$\lambda_i < 0.20$$ (of the correlation matrix), where the weight $$1/\lambda_i$$ amplifies small deviations that violate the normal correlation structure.

  <p>
  $$T_{\text{minor}}(\mathbf{z}) = \sum_{i=p-r+1}^{p} \frac{y_i^2}{\lambda_i}.$$
  </p>

The minor statistic resembles Aggarwal's *hard PCA* <d-cite key="aggarwal2017"></d-cite>, which scores observations only along low-variance components. By pairing it with $$T_{\text{major}}(\mathbf{z})$$, the PCC also captures extreme values along the dominant directions that hard PCA misses. In contrast to a single combined score, the two statistics also indicate which type of anomaly an observation represents.

**Classification**\
To classify an unseen observation $$\mathbf{z}$$, anomaly thresholds $$c_1$$ and $$c_2$$ are defined for the major and minor statistics. An observation is flagged as anomalous if either threshold is exceeded:

<p>
$$T_{\text{major}}(\mathbf{z}) > c_1 \quad \text{or} \quad T_{\text{minor}}(\mathbf{z}) > c_2 .$$
</p>

The thresholds $$c_1$$ and $$c_2$$ are the $$(1 - \alpha_1)$$- and $$(1 - \alpha_2)$$-quantiles of the empirical distributions of the two statistics on the training data, chosen according to individual false alarm rates $$\alpha_1$$ and $$\alpha_2$$ to achieve an overall false alarm rate of $$\alpha = \alpha_1 + \alpha_2 - \alpha_1 \alpha_2$$, assuming that the two statistics are independent.

## Appendix B
<a id="pyods_pca"></a>
**Overview of the differences between the PCC and PyOD**

| Step | Shyu et al. | PyOD (defaults) | Impact |
|---|---|---|---|
| Standardization | sample std. (`ddof=1`) | `StandardScaler` (`ddof=0`) | negligible |
| Decomposition | eigendecomposition of $$\mathbf{R}$$ | SVD of the standardized data | identical up to the sign of each component |
| Trimming | remove the $$\gamma \cdot n$$ most extreme observations ($$\gamma = 0.005$$) | none | less robust to outliers in the training data |
| Components | $$q$$ major and $$r$$ minor, evaluated separately | all $$p$$ components in a single sum | major and minor anomalies are not distinguished |
| Threshold | $$c_1$$, $$c_2$$ from false alarm rates $$\alpha_1$$, $$\alpha_2$$ | one quantile of the training scores (`contamination=0.1`) | a single threshold |
| Score | $$\sum_i \frac{y_i^2}{\lambda_i}$$ per statistic| $$p \sum_i \frac{\lVert \mathbf{z} - s_i \mathbf{e}_i \rVert}{\lambda_i}$$ | different function (see [What PyOD computes](#what-pyod-computes)) |

**Standardization**\
The `StandardScaler` <d-cite key="standardscaler"></d-cite> divides by the biased standard deviation (`ddof=0`). According to the documentation this choice is unlikely to affect the model performance.

**Decomposition**\
scikit-learn, which is used by PyOD, computes the components via a singular value decomposition of the standardized data instead of an eigendecomposition of the correlation matrix. Both yield the same components, but only up to their sign: if $$\mathbf{e}_i$$ is a unit eigenvector of $$\mathbf{R}$$, so is $$-\mathbf{e}_i$$. Implementations therefore fix the sign by convention, such as `svd_flip` in scikit-learn <d-cite key="sklearnPCA"></d-cite> and the resulting sign has no meaningful interpretation in terms of the dat <d-cite key="broResolvingSignAmbiguity2008"></d-cite>. For Shyu's score this is irrelevant, because $$y_i$$ enters the statistic squared. For PyOD's score it is not, as shown in [Problem 2](#problem-2).

**Trimming**\
PyOD fits the PCA on all training observations. Outliers in nominally normal training data can inflate the estimated variances and rotate the components <d-cite key="shyu2003"></d-cite>, so that anomalies partly become part of the learned normal subspace <d-cite key="ringbergSensitivityPCATraffic2007a"></d-cite>. Shyu et al. prevent this by trimming.

**Component Selection**\
By default, PyOD uses all $$p$$ components. If `n_components` is set to $$k < p$$, only the $$k$$ components with the largest variance are retained. `n_selected_components` then selects the *last* of these for scoring. They correspond to minor components in the sense of Shyu et al. only if $$k = p$$. PyOD provides no option to evaluate major and minor components separately.

## Appendix C

**Expanding the distance to an eigenvector tip**

Norm as a dot product

<p>
$$\lVert \mathbf{z} - s_i \mathbf{e}_i \rVert^2 = (\mathbf{z} - s_i \mathbf{e}_i)'(\mathbf{z} - s_i \mathbf{e}_i)$$
</p>

Expand it, and as the dot product is symmetric, we can combine the two middle terms

<p>
$$(\mathbf{z} - s_i \mathbf{e}_i)'(\mathbf{z} - s_i \mathbf{e}_i) = \mathbf{z}'\mathbf{z} \;-\; s_i\, \mathbf{z}'\mathbf{e}_i \;-\; s_i\, \mathbf{e}_i'\mathbf{z} \;+\; s_i^2\, \mathbf{e}_i'\mathbf{e}_i = \mathbf{z}'\mathbf{z} \;-\; 2\, s_i\, \mathbf{e}_i'\mathbf{z} \;+\; s_i^2\, \mathbf{e}_i'\mathbf{e}_i$$
</p>

Now we substitute

| Term | Value | Reason |
|---|---|---|
| $$\mathbf{z}'\mathbf{z}$$ | $$\lVert \mathbf{z} \rVert^2$$ | definition of the norm |
| $$\mathbf{e}_i'\mathbf{z}$$ | $$y_i$$ | Shyu et al., Eq. (4): $$y_i = \mathbf{e}_i'\mathbf{z}$$ |
| $$s_i^2$$ | $$1$$ | $$s_i \in \{-1, +1\}$$ |
| $$\mathbf{e}_i'\mathbf{e}_i$$ | $$1$$ | eigenvectors have unit length (`components_` is orthonormal) |

This gives:

<p>
$$\lVert \mathbf{z} - s_i \mathbf{e}_i \rVert^2 = \lVert \mathbf{z} \rVert^2 - 2\,s_i\,y_i + 1$$
</p>

Take the square root

<p>
$$\lVert \mathbf{z} - s_i \mathbf{e}_i \rVert = \sqrt{\lVert \mathbf{z} \rVert^2 - 2\,s_i\,y_i + 1}$$
</p>

## Appendix D

**Scores proposed in earlier reports**

In 2020 pull request #211 <d-cite key="pyodPR211"></d-cite> implemented the correct projection, but normalized the squared scores by the explained variance ratio instead of the eigenvalue $$\lambda_i$$. This scales all scores by the total variance $$\sum_j \lambda_j$$, preserving the exact Mahalanobis ranking while changing the numerical values. With the default `whiten=False`, the proposal in Issue #217 <d-cite key="pyodIssue217"></d-cite> is equivalent to #211. Enabling `whiten=True` causes `fit_transform` to return already normalized scores $$t_i = y_i / \sqrt{\lambda_i}$$, so each component is weighted by $$1/\lambda_i^2$$ instead of $$1/\lambda_i$$.

In 2021, pull request #340 <d-cite key="pyodPR340"></d-cite> took up the idea of #217, but centers with the mean of the current batch instead of the training mean. As a result, a test sample scored on its own always gets a score of 0. In addition, the weight is placed inside the square, so the components are weighted by $$1/\lambda_i^2$$ instead of $$1/\lambda_i$$.

The following table summarizes the scores.

|version | score |
|---|---|
| current PyOD | $$\sum_i \frac{\lVert \mathbf{z} - \mathbf{e}_i \rVert_2}{\lambda_i / \sum_j \lambda_j}$$|
| [#211](https://github.com/yzhao062/pyod/pull/211) | $$\sum_i \frac{y_i^2}{\lambda_i / \sum_j \lambda_j}$$|
| [#217](https://github.com/yzhao062/pyod/issues/217) | $$\sum_i \frac{t_i^2}{\lambda_i / \sum_j \lambda_j}$$|
| [#340](https://github.com/yzhao062/pyod/pull/340) | $$\sum_i \left(\frac{t_i - \bar{t}_i^{\text{batch}}}{\lambda_i / \sum_j \lambda_j}\right)^2$$ |
| ours | $$\sum_i \frac{y_i^2}{\lambda_i}$$ |

where $$y_i = \mathbf{e}_i^\top \mathbf{z}$$ denotes the projection of the standardized observation $$\mathbf{z}$$ onto eigenvector $$\mathbf{e}_i$$, and $$t_i$$ denotes the output of sklearn's transform ($$t_i = y_i$$ for`whiten=False`, and $$t_i = y_i / \sqrt{\lambda_i}$$ for `whiten=True`)
